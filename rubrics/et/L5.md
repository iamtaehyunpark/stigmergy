# Rubric L5 — Loom API documentation suite from contradictory fragments (frozen v2, before any ET run)

Audience: developers integrating against the Loom API; the docs ship only
if they agree with each other and with the canonical inventory.

Required elements (completeness):
1. A canonical API inventory that states the reconciled CURRENT (2.2)
   surface AND records reconciliation decisions with justifications —
   visibly derived from the fragments, not generic.
2. All four documents present and substantive: getting-started tutorial,
   endpoint reference for 2.2, v1-to-v2 migration guide, troubleshooting
   FAQ.
3. The reference covers the reconciled surface: POST /executions,
   GET /executions/{id}, POST /executions/{id}/cancel, PUT /hooks,
   POST /workflows, GET /workflows/{id}/versions; X-Loom-Key
   authentication; statuses queued/running/succeeded/failed/cancelled;
   webhook events execution.succeeded/execution.failed/execution.cancelled;
   limits (rate limit, definition size, accepted formats).
4. The migration guide covers at minimum: /run → /executions (and that
   the alias was removed in 2.1, earlier than announced), Bearer-on-
   Authorization → X-Loom-Key (v1 Bearer only on the /v1/* legacy
   prefix), webhook event renames (execution.finished removed), new
   statuses/cancel capability, and changed limits.

Accuracy (reconciliation correctness against the fragments):
- Deprecated /run alias treated as REMOVED (F2 supersedes F1's "until
  2.2" promise); docs that still document /run as available are wrong.
- Rate limit resolved to 120 requests/min (F6, versioned 2.2) with the
  memo's 100 (F7, undated) superseded or explicitly flagged — silently
  adopting 100 (or 60) is a defect.
- execution.finished absent from current docs (F9); execution.cancelled
  present (F10) despite being undocumented in the sources.
- Workflow uploads: YAML and JSON, 1 MB (F12 supersedes F11).
No invented endpoints, parameters, or auth schemes beyond reasonable
elaboration of the fragments.

Structure: inventory discoverable and decision-per-contradiction; each
document organized for its stated purpose; FAQ grounded in the actual
tickets/pitfalls the fragments describe.

Consistency (weighted heaviest at this level): zero disagreement between
any document and the inventory, and between documents — endpoint names,
header names, event names, statuses, and limits identical everywhere.
A documented decision changed in one document but not another is the
defining defect of this level.
